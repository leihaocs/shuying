# 双机出包约定（Mac + Windows）

> 适用对象：**Android 包**。
> iOS 与鸿蒙仍**只在 Mac 出包**，不在本文范围内。
> 制定日期：2026-10-23，基于「家里 Mac + 办公 Windows 共用同一发布密钥」的工作方式。

---

## 一、权限边界

| 事项 | Mac（家里） | Windows（办公室） |
|---|---|---|
| Android 调试包 | ✅ | ✅ |
| Android 正式包（可上架） | ✅ | ✅ |
| iOS 编译、上传、TestFlight | ✅ | ❌ 需 Xcode / Transporter |
| 鸿蒙 `.app` 打包 | ✅ | ❌ 需 DevEco / macOS 工具链 |
| 文档、软著材料 | ✅ | ✅ |

iOS 与鸿蒙的限制来自工具链（Xcode、DevEco 无 Windows 版），是硬约束，不是人为约定。

## 三、五条纪律（必须遵守）

| # | 纪律 | 原因 |
|---|---|---|
| 1 | **同一版本只在一台机器出包** | `versionCode` 不能重复，否则商店拒收；另一台只做验证 |
| 2 | **出包前 `git pull`，出完把版本号改掉并 commit + push** | 保证构建号全局唯一、可追溯 |
| 3 | `key.properties` 和 `.jks` **永不入库** | 密钥现在存在于两台机器，泄露面翻倍，不能再扩散到 git |
| 4 | **两端 Flutter 版本保持一致** | 否则同一份代码两端产物不同，出问题无法复现 |
| 5 | 产物放 `dist/`（已忽略），**不入库** | 仓库只放源码与文档 |

## 四、标准出包流程

### 出包前（两台都一样）

```bash
git pull                     # 1. 先同步
flutter --version            # 2. 确认与另一台版本一致
# 3. 递增构建号：编辑 flutter_app/pubspec.yaml 的 version: 1.0.0+N
#    N 必须是两端都没用过的新数字
```

### 出包

```bash
# 调试包（全架构）
flutter build apk --debug --flavor direct

# 正式包（可上架）
flutter build apk --release --flavor direct
```

Windows 侧也可用一键脚本：`C:\dev\出调试包.bat`

### 出包后

```bash
git add flutter_app/pubspec.yaml
git commit -m "chore: 安卓构建号升至 1.0.0+N（<机器名> 出包）"
git push
```

产物归档到 `dist/1.0.0+N/`，不进 git。

## 五、版本与构建号管理

- 版本号与构建号都在 `flutter_app/pubspec.yaml`：`version: 1.0.0+N`
- `N` 即 Android 的 `versionCode`，**全局唯一、只增不减**
- 谁出包谁负责改 `N`，出完立刻 push，让另一台机器看到
- 不确定 `N` 用没用过，先 `git pull` 看当前值，或查商店后台已上传的最大 versionCode

## 七、密钥备份要求

密钥现存在于**两台物理机器**，风险面是单机的两倍，请遵守：

1. `.jks` 与 `key.properties` 只通过 **U 盘 / 加密介质 / 密码管理器**传递
2. **不放云盘、不放 git、不截图、不发聊天工具**
3. 其中一台机器重装或报废前，先从另一台确认密钥可恢复
4. 若怀疑泄露：重新生成密钥 → 但**已上架商店的包无法换签名**，只能在换新包名时才能换，所以预防优先于补救
